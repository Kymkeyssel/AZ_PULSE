1. Objet et vision fonctionnelle
AZ PULSE est le système d’information web intégré d’AZ CORPORATION. Sa fonction est de centraliser les activités, relier les informations métier, faciliter le pilotage et fournir des capacités d’analyse, d’intelligence artificielle et d’automatisation sans transformer l’application en ensemble de modules isolés.
Vision centrale
Une donnée métier doit être créée une seule fois lorsque cela est pertinent, disposer d’une source de vérité, conserver ses relations et pouvoir alimenter d’autres processus selon les droits de l’utilisateur.
CRM → Workspace → Knowledge Hub / Infrastructure → Analytics → Dashboard → AI Workspace → automatisations n8n
L’objectif fonctionnel n’est donc pas seulement de proposer des écrans, mais de démontrer une circulation cohérente de l’information. Une opportunité commerciale peut par exemple aboutir à un projet ; le projet produit des tâches et des documents ; l’avancement alimente les indicateurs ; l’IA interprète les données autorisées ; une automatisation peut ensuite notifier un responsable.

5. Gouvernance des accès et authentification
Principe de contrôle
Le demandeur fournit son identité et le contexte de sa demande, mais ne choisit pas son rôle ni ses permissions. L’entreprise valide la demande, attribue les droits et conserve la traçabilité des décisions.
5.1. Processus de demande d’accès
Demandeur → demande d’accès → PENDING → validation entreprise → rôle + permissions → création du mot de passe → activation → espace personnel
La demande initiale ne contient pas de mot de passe.
Le demandeur renseigne son identité, sa situation/contexte et la justification de son besoin.
Après approbation, l’écran de suivi permet de définir le mot de passe et sa confirmation.
La validation du mot de passe active le compte et ouvre l’espace personnel correspondant au rôle attribué.
Le statut d’une demande peut notamment être PENDING, MORE_INFO_REQUIRED, APPROVED, REJECTED ou CANCELLED.
5.2. Répartition des pouvoirs
Le Super Admin gouverne la plateforme, les administrateurs, les rôles, permissions et paramètres techniques.
L’Admin / Direction gère les utilisateurs et les demandes d’accès selon son périmètre, sans administrer les autres administrateurs ni la configuration technique profonde.
Les changements sensibles de rôle ou de permissions doivent être journalisés.
5.3. Modèle d’autorisation
Utilisateur + rôle + permission + périmètre = autorisation réelle
Le backend Symfony reste l’autorité sur les autorisations. React ne fait qu’adapter l’expérience et masquer ou présenter des fonctionnalités selon les droits connus ; il ne constitue jamais la barrière de sécurité principale.

7. Formation et gestion des paiements
Le domaine Formation possède une logique métier propre. Les paiements de formation ne sont pas effectués dans AZ PULSE : ils sont réalisés en banque. AZ PULSE sert à enregistrer et suivre la preuve de paiement, sans connexion directe à la banque.
7.1. Principe financier
Les frais de formation appartiennent à la Formation.
L’inscription matérialise l’entrée de l’apprenant dans une session et porte les informations d’inscription correspondantes.
Les paiements peuvent être réalisés en plusieurs tranches.
Le paiement est enregistré dans AZ PULSE à partir d’un justificatif bancaire.
7.2. Workflow d’enregistrement du paiement
Banque → reçu bancaire → dépôt dans AZ PULSE → OCR / extraction Python → vérification → validation Formation → enregistrement du paiement → génération du reçu AZ PULSE → mise à jour du suivi Formation
Le Parent ou l’Apprenant peut déposer le justificatif dans un espace de dépôt.
Symfony contrôle le fichier, l’utilisateur et le contexte.
FastAPI peut extraire les informations du justificatif avec un service OCR ; un LLM peut être utilisé en complément lorsqu’une interprétation plus complexe est nécessaire.
Le système ne doit pas considérer automatiquement le paiement comme validé uniquement sur la base de l’OCR.
Un responsable Formation vérifie les informations extraites et valide, corrige ou rejette le justificatif.
Après validation, Symfony enregistre le paiement et génère un reçu AZ PULSE, imprimable ou téléchargeable.

8. Infrastructure & IT et intégration GLPI
GLPI reste le système spécialisé pour l’inventaire technique du parc. AZ PULSE constitue la couche d’intégration, de consultation métier, de pilotage, d’analyse et de présentation adaptée aux utilisateurs.
Principe d’intégration
React ne communique pas directement avec GLPI. Le frontend appelle Symfony ; Symfony utilise un service d’intégration GLPI ; ce service communique avec l’API GLPI.
GLPI Agent → GLPI → API GLPI → service d’intégration Symfony → données Infrastructure AZ PULSE → Dashboard / Analytics / IA

8.2. Interface Parc informatique
L’ensemble du parc est affiché dans un écran principal de type tableau, inspiré de la logique de GLPI.
Il n’est pas nécessaire de créer une page dédiée à chaque équipement.
La table peut être dense, filtrable et extensible afin de restituer l’ensemble des champs techniques sans sacrifier la lisibilité.
Un panneau latéral peut présenter le détail d’une ligne sélectionnée sans quitter le Parc informatique.
Les données provenant de GLPI doivent être identifiables comme telles et ne pas être confondues avec les données métiers natives d’AZ PULSE.
9. Intelligence artificielle avec FastAPI
AZ PULSE n’entraîne pas et n’héberge pas son propre modèle de langage. Le service Python/FastAPI orchestre des agents et appelle un fournisseur de modèles par API avec une clé secrète conservée côté service IA.
React → Symfony → FastAPI → fournisseur LLM / services IA → FastAPI → Symfony → React

17. Règles structurantes à préserver
Une donnée métier structurante ne doit pas être dupliquée inutilement dans plusieurs modules.
Le backend Symfony reste l’autorité sur les données, les permissions et l’exécution des actions métier.
Le frontend React ne doit pas servir d’autorité de sécurité.
FastAPI ne doit pas devenir une base métier parallèle ni contourner Symfony pour accéder à PostgreSQL.
L’IA reçoit uniquement le contexte autorisé pour l’utilisateur concerné.
Une recommandation IA ayant un impact métier doit être validée par une personne habilitée avant son exécution.
n8n ne doit pas contenir les règles métier centrales ; il orchestre des workflows simples.
GLPI reste le système spécialisé pour l’inventaire technique ; l’intégration passe par Symfony.
Le paiement de formation est réalisé en banque ; AZ PULSE enregistre la preuve et le résultat de validation, sans connexion bancaire directe.
Les interfaces changent selon les profils, rôles et permissions, même lorsque plusieurs utilisateurs accèdent au même module.
Les changements sensibles d’accès et de permissions doivent laisser une trace d’audit.
Les cas d’utilisation détaillés doivent rester des actions concrètes, avec un début, un traitement et un résultat observable.
Conclusion
AZ PULSE est conçu comme un système d’information intégré : le CRM génère le contexte commercial, Workspace organise l’exécution, Formation gère le parcours académique, Knowledge Hub capitalise l’information, Infrastructure s’appuie sur GLPI pour le parc IT, Analytics mesure, Dashboard pilote, FastAPI apporte l’intelligence spécialisée et n8n automatise les flux simples. Symfony reste le noyau métier, de sécurité et de contrôle.
Synthèse fonctionnelle
Une donnée métier → un référentiel maître → des relations explicites → des événements → pilotage / IA / automatisation selon les droits
La valeur d’AZ PULSE repose sur l’interconnexion des espaces et des modules, tout en maintenant des expériences distinctes pour les utilisateurs. Les mêmes données peuvent être consultées ou exploitées différemment selon le profil, le rôle, les permissions et le périmètre autorisé.
Points à verrouiller en conception détaillée
Référentiel maître et règles de modification pour chaque donnée structurante.
Permissions et périmètres exacts de chaque rôle, notamment Admin, Direction et Responsables métier.
États et règles de transition détaillés pour les demandes d’accès, opportunités, projets et parcours Formation.
Contrat d’échange Symfony → FastAPI et format structuré des réponses IA.
Périmètre exact de synchronisation GLPI et responsabilités respectives entre GLPI et AZ PULSE.
KPI réellement retenus pour la Direction et pour chaque responsable de module.
